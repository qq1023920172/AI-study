# W8 · 合规：把技术发现翻译成甲方能拿去备案的语言

> 前六周你回答的是「这个系统有多不安全」。
> W8 要回答的是另一个问题：**「这个系统能不能过审、能不能上线、缺什么材料」。**

---

## 一、合规 ≠ 安全

这是这一周最重要的认知转变：

| | 安全 | 合规 |
|---|---|---|
| 目标 | 降低被攻破的概率 | **证明你采取了措施** |
| 成功标准 | 攻击没成功 | **文档、日志、流程齐全** |
| 谁来判断 | 攻击者 | 审核方 |
| 证据形态 | 复现步骤 | 制度文件、记录、截图 |

**一个技术上很安全的系统，如果拿不出《语料来源说明》《安全评估报告》《投诉处理记录》，照样过不了。**

反过来，一个技术上很脆弱的系统，只要材料齐全，可能先上线了。

所以 W8 不是继续找漏洞，是**把 W6 的发现，映射到监管要求上，算出差距**。

## 三、核心方法：三张表

### 表一：条款清单（要求侧）

把标准拆成可勾选的条目。每条要有：编号、类别、要求（一句话）、判据（怎么算满足）。

### 表二：证据清单（现状侧）

针对每条要求，指出**现有系统里对应什么**：
- W6 的某条发现
- 某段代码 / 某份配置
- 「不存在」也是一种答案

### 表三：差距表（结论侧）

| 状态 | 含义 | 处理 |
|---|---|---|
| **满足** | 有措施且有证据 | 归档 |
| **部分满足** | 有措施但缺证据，或措施不完整 | 补材料或补措施 |
| **不满足** | 没有对应措施 | 排期 |
| **不适用** | 该条不涉及本系统 | 写明理由 |

**「部分满足」是最常见的状态，也是最容易被审核挑出来的。** 有措施但拿不出证据，在合规上等于没有。

## 六、四个最容易漏的点

这些不是技术漏洞，但**审核一定看**：

| 项 | 要求 | 你的系统有吗 |
|---|---|---|
| **AI 生成内容标识** | 输出需可识别为 AI 生成 | ？ |
| **用户协议** | 明示禁止用途、责任划分 | ？ |
| **投诉举报渠道** | 有入口、有处理记录 | ？ |
| **日志留存** | 输入输出可追溯，留存期限 | ？ |

**这四项在 W1–W6 里一次都没测过。** 它们不影响安全，但直接决定能不能上线。

```
W6：这个系统有多不安全   → 7 条发现，带风险分
W8：这个系统合不合规     → 同一批发现，换一套坐标系
```

同一个「任意文件读取」：

- 在 W6 里是 **AG-01，18 分，严重**
- 在 W8 里对应「安全措施—模型输出安全」和「数据安全—访问控制」，状态是**不满足**

**技术结论不变，但表达方式必须换。** 甲方拿去备案的，是后者。
